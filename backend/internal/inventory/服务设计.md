# 库存微服务设计笔记

## 核心设计原则（总）

**业务永远正确（DB），性能尽力而为（Redis），问题自动修复（定时任务）**

### 架构三层保障
1. **Redis削峰**：Lua原子预扣，挡住高并发，**35分钟TTL**保证幂等（比订单30分钟超时长5分钟，避免边界case）
2. **DB裁判**：事务写操作记录+扣库存，唯一索引保证幂等，行锁防超卖
3. **定时兜底**：小时增量+每日全量，修复Redis失败导致的缓存不一致

### 容错策略
- Redis全挂 → 业务继续（降级走DB）
- Redis部分失败 → 仅告警（定时任务修复）
- 网络重试 → 幂等保护（operation_id唯一索引）

---

预扣设计要点
预扣本质 = 锁定资源，防止超卖/超用

两种模式：

数量型（库存）→ 减数量
实例型（优惠券）→ 状态转移
为什么库存用Redis：

热点数据（多人抢同一商品）
MySQL扛不住高并发写同一行
Redis挡请求，DB做最终裁判
优惠券不需要Redis：

分散数据（每人用自己的券）
MySQL直接UPDATE够用

## 详细设计（分）

### 1. 服务边界
- 只负责库存数量一致性
- 不关心订单业务流程

---

### 2. 数据模型

**分层职责**：DB = 真理，Redis = 快速验证

#### DB（最终事实）
- total_stock
- available_stock
- sold_stock
- 不存预扣状态

#### Redis（资格缓存）
- 抗并发、挡请求
- 数据可丢、可重建

---

### 3. 核心链路

#### 下单（预扣）
下单请求
→ bff 秒杀限流  
→ Redis Lua 预扣库存（ReserveStock）  
→ 返回下单结果

#### 支付成功（确认）
订单已支付，发消息 
→ 库存消费者消费消息，幂等 CommitStock 
→ DB 事务：加锁（查，扣减库存） + 写操作记录（幂等）

---

### 4. 幂等设计

**原则**：operation_id全局唯一，DB唯一索引保证只执行一次

- 规则：order_id + ":" + operation_type
- 操作记录与库存扣减必须在同一事务
- 唯一索引冲突 → 返回`ErrDuplicateOperation`（业务判断是否重试）

---

### 5. 超卖处理
- 并发超卖：DB 行锁 / 乐观锁
- 重复扣减：幂等 + 事务

---

### 6. 并发控制

**原则**：请求并发不限制，DB并发必须限制

#### DB 并发控制
- 同步接口：semaphore(channel，不忙等，阻塞)
- 秒杀场景：worker pool（进一步升级，不阻塞，任务入队即返回）

#### Worker Pool 参数
- worker ≈ DB CPU 核 × 2~4
- queue ≈ worker × 10~100
- 队列满直接失败

---

### 7. 预扣记录删除策略

**原则**：根据业务场景选择 - CommitStock自然过期，ReleaseStock主动删除

#### 背景
CommitStock/ReleaseStock 成功后，是否应该主动删除 Redis 预扣记录？

#### 最终策略

**CommitStock：不删除（✅自然过期）**
- 原因：支付成功后仍可能有网络延迟重试，需保留记录35分钟保证幂等（订单超时30分钟 + 5分钟缓冲）
- 实现：`return nil` （不操作Redis，让TTL自然过期）
- 幂等：DB唯一索引 + Redis记录存在性

**ReleaseStock：主动删除（✅立即清理）**
- 原因：订单取消后不会再有CommitStock，可安全删除
- 实现：Lua脚本原子操作：恢复库存 + 删除记录
- 幂等：记录不存在 → 直接返回成功（已释放或已过期，不会重复恢复库存）
- 关键洞察：删除后重试时，检查记录不存在就返回成功，**不会再操作库存**，因此安全

#### 方案演进

**方案1：立即删除（❌ CommitStock有风险）**
- 理由：幂等已完成，节省内存
- 问题：延迟重试会丢失幂等保护窗口

**方案2：自然过期（✅ CommitStock采用）**
- 理由：35分钟（订单30分钟+5分钟缓冲）覆盖所有重试场景，内存成本几百字节可忽略
- 实现：不删除，让TTL自然过期
- 关键：避免订单刚好30分钟时取消，但Redis记录已过期的边界情况

**方案3：拆分标记+数据（过度设计）**
- 适用：详细数据KB级别
- 当前：预扣数据仅几百字节，不值得

```go

- 网络抖动/超时重试都发生在短时间内（秒/分钟级）
- 30分钟足够覆盖所有异常重试场景
- 牺牲少量内存（每条几百字节），换取完全的幂等性保证

```

**适用场景：**
- 详细数据较大（KB 级别）
- 需要节省内存成本

**当前场景不适用：**
- 预扣数据很小（productID + quantity，几百字节）
- 增加复杂度，收益不大

### 8. Redis缓存一致性保障

**原则**：DB是真理，Redis失败不阻塞业务，定时任务异步修复

#### 三层保障机制

**1. DB幂等（第一道防线）**
- `(operation_id, product_id)` 唯一索引
- 保证退款操作只入库一次

**2. 容错执行（第二道防线）**
- Redis读取失败 → 仅告警，返回成功
- Redis写入部分失败 → 记录失败商品，告警后返回成功
- 关键：**DB已正确，业务无损**

**3. 定时任务兜底（第三道防线）**
- 每小时增量巡检：扫描最近1小时退款
- 每日全量对账：凌晨3点深度检查
- 差异超阈值 → 强制同步 + 告警

#### RefundStock容错实现
```go
// 1. DB事务成功（强一致性保证）
db.Transaction(插入退款记录 + 恢复库存)

// 2. Redis恢复（容错执行，失败不中断）
for _, product := range products {
    if err := cache.IncrBy(...); err != nil {
        log.Warn("Redis恢复失败", err)  // 仅告警
        continue  // 不return，继续其他商品
    }
}
return nil  // DB成功即业务成功
```

- 每小时对比DB退款记录 vs Redis预库存差异
- 差异 > 10个商品 → 触发P1告警

### 9. 定时任务实现（兜底修复）

**原则**：小时增量快速响应 + 每日全量深度清理

#### 任务设计

**每小时增量巡检（快速响应）**
- 执行：每小时整点
- 逻辑：查最近1小时退款 → 对比Redis差异 → 超阈值(10)强制同步
- 优点：快速发现，扫描范围小，压力低

**每日全量对账（深度清理）**
- 执行：凌晨3点
- 逻辑：查最近7天活跃商品 → 全量对比 → 差异超5%或10修复
- 优点：系统性检查，大量差异触发P1告警

#### 核心SQL
```sql
-- 小时增量：找出最近1小时退款
SELECT product_id, SUM(quantity) 
FROM inventory_operations 
WHERE type='refund' AND created_at > NOW() - INTERVAL 1 HOUR
GROUP BY product_id;

-- 差异检查
if abs(dbStock - redisStock) > 10 {
    Redis.Set("stock:{productID}", dbStock, 30min)
}
```

#### 调度方案

**方案A：Cron库（推荐）**
```go
c := cron.New()
c.AddFunc("0 * * * *", repairJob.RunHourly)    // 每小时整点
c.AddFunc("0 3 * * *", repairJob.RunDaily)     // 每日凌晨3点
c.Start()
```
优点：轻量无依赖，与服务同生命周期

**方案B：消息队列延时任务（大厂）**
- 适用：分布式多实例部署
- 缺点：需要MQ基础设施

#### 监控指标

**实时指标**：
- Redis写入失败率（Warn级日志统计）
- RefundStock中Redis错误数

**定时巡检指标**：
- 每小时修复的商品数量
- 每日对账差异商品数量

**告警规则**：
- 实时：单次RefundStock Redis错误 > 0 → P2告警
- 小时：修复商品数 > 5 → P2告警
- 每日：修复商品数 > 10 → P1告警（系统性问题）

如何防止超卖？
